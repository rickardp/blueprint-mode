<!-- SECTION: layout -->
## Directory Layout

```
docs/                       # Code / architecture tree (engineering reviewers)
├── specs/
│   ├── product.md          # Vision, users, success metrics
│   ├── tech-stack.md       # Technology choices, pointing at ADRs
│   ├── boundaries.md       # Safe without asking / Ask first / Never
│   ├── features/*.md       # Feature specs (discovered by globbing)
│   └── non-functional/*.md # NFRs by category (discovered by globbing)
└── adrs/NNN-[slug].md      # Architecture decisions (discovered by globbing)
patterns/                   # Examples for any subject: code, schema, UI, scripts
├── good/[name].[ext]       # Approved examples
└── bad/anti-patterns.md    # Anti-patterns to avoid
design/                     # Design / UX tree, opt-in via /blueprint-mode:onboard-design
└── ux-decisions/NNN-[slug].md
DESIGN.md                   # Optional community-format design context, adjacent to Blueprint
CLAUDE.md or AGENTS.md      # Agent instructions
```

No index files. Everything is discovered by globbing and status is read from frontmatter.

<!-- SECTION: working-style -->
## Working Style for Skills

- A skill invocation is the scope. Produce the complete result; do not ask what to create or offer full-versus-partial choices, and do not pause for a preview before writing.
- Ask only about content you cannot find: why a technology was chosen, who the users are. Put all such questions in one message, accept "skip", and write `TBD` for what stays unknown. Create files first with TBD, then upgrade them when answers arrive.
- Extract everything from the argument first. "PostgreSQL because the team knows it" already contains the decision and the rationale.
- Prefer Draft over a forced Active status when rationale is thin. Decisions evolve.
- Report what was created and where, then stop.

<!-- SECTION: agent-file-detection -->
## Agent Instructions File Detection

Run `ls -la CLAUDE.md AGENTS.md`. If one is a symlink to the other, edit the target only and never delete or recreate either. If one only says "See the other", edit the referenced one. If both exist independently, update both. If neither exists, create `CLAUDE.md`.

A file generated by Blueprint 1.x has sections named `CRITICAL: Pre-Edit Checklist`, `Architecture Decisions`, `Documentation`, `Code Comments`, `Pattern Discovery`, `Creating Documentation`, and `BOUNDARY VIOLATIONS`. Replace those sections as one block with the current `agent-instructions` template. Keep the Commands section and anything Blueprint did not write.

<!-- SECTION: design-separation -->
## Code Tree vs Design Tree

`docs/**` and `patterns/**` are reviewed by engineering. `design/**` is reviewed by design and exists only after `/blueprint-mode:onboard-design`. The two are never mixed: UX decisions are not ADRs, and each tree numbers independently.

| Concern | Goes to |
|---------|---------|
| Tech or architecture choice, library, infra, code-level pattern | `docs/adrs/` |
| One UX choice with alternatives (modal vs page, navigation model, copy for a flow) | `design/ux-decisions/` when the tree exists |
| Cross-cutting design rule or prohibition (palette limits, voice, type scale) | `DESIGN.md` when present or the user agrees to scaffold it |
| Functional or non-functional requirement | `docs/specs/` |
| Example or anti-pattern, any subject | `patterns/` |

`DESIGN.md` is a community convention (Google Stitch, awesome-design-md) that Blueprint stays compatible with but does not own. UX decisions reference its rules instead of restating them.

Undocumented UI code is implementation state, not design intent. Capture a UX decision only when a person states why the choice should persist. When the design tree is missing and the input is clearly UX, say so once and offer `/blueprint-mode:onboard-design`; never file UX rationale under `docs/adrs/` silently. When the input is plainly architectural and the repo has no design surface, do not mention design at all.

## docs/specs/features/[feature].md

```markdown
---
status: Planned | Active | Deprecated
maturity: Exploring | Building | Hardening | Stable
module: src/[module]/
related_adrs: []
---

# [Feature Name]

## Overview
[One or two sentences]

## User Stories
- As a [user type], I want [capability] so that [benefit]

## Requirements
- [Requirement]

## Implementation State

**Current focus:** [What is being worked on, or "None"]

| Milestone | Status |
|-----------|--------|
| [milestone] | Done / In Progress / Not Started |

**Open questions:**
- [Unresolved question]

**Constraints:**
- [Active constraint]

## Acceptance Criteria (optional)
- Given [context], when [action], then [outcome]
```

Maturity: Exploring (idea, sparse spec), Building (active development), Hardening (complete, stabilizing), Stable (low churn). It can move backwards. Specs written by Blueprint 1.x lack `maturity` and Implementation State; add them when touching such a spec.

<!-- SECTION: boundaries -->
## docs/specs/boundaries.md

Boundaries tell an agent where it has autonomy, where to check in, and what is off limits. Grant autonomy explicitly for safe work; modern models already test and verify without being told. Obligations such as "run lint before commit" belong in the Commands section of the agent instructions, not here.

```markdown
# Agent Boundaries

## Safe Without Asking

- Run tests, linters, and type checks; fix failures caused by your change and rerun. Report pre-existing failures instead of fixing them.
- Edit and refactor code inside existing modules
- Add or update dev and test dependencies
- Record a decision, pattern, or requirement the user stated

## Ask First

### Breaking Changes
- Removing or renaming public API fields
- Destructive or backward-incompatible schema changes (dropping or retyping columns, changing keys)

### Dependencies
- Adding a runtime dependency or upgrading a major version

### Security
- Changes to authentication or authorization

### [Project-specific]
- [Item]

## Never Do

### Security
- Commit secrets or credentials
- Disable authentication or security checks

### Repository
- Push to the default branch or rewrite shared history
- Create Markdown files outside the Blueprint structure without agreement

### [Project-specific]
- [Item]

## Scoped Rules (optional)

### src/[module]/
- [Module-specific rule]
```

A file written by Blueprint 1.x has `## Always Do` instead of `## Safe Without Asking`, and it holds obligations ("read ADRs before implementing", "run quality commands before commits") rather than grants. When migrating, drop the pre-read obligations (agent instructions now route conditionally), move command obligations to the agent instructions, and keep only true autonomy grants under the new heading.

<!-- SECTION: adr-template -->
## docs/adrs/NNN-[slug].md

Status: Draft (emerging, TODOs allowed), Active (settled), Superseded (`superseded_by:` set to the new file's stem), Deprecated (`deprecated_date:` and `deprecated_reason:` set). When the last `<!-- TODO: -->` in a Draft is resolved, set `status: Active`. The next number is one past the highest in `docs/adrs/`.

The slug describes the current title. If a retitle makes it stale, rename the file, then search for the old basename and its extensionless stem (`superseded_by` uses the stem) and update those references; leave number-only references such as `ADR-NNN` and `related_adrs` alone.

Canonical vocabulary: frontmatter `status`, `**Positive:**` and `**Negative:**` under Consequences, and `## Related`. `/blueprint-mode:validate` flags synonyms such as Benefits, Trade-offs, References, or "Accepted".

```markdown
---
status: Active
date: [TODAY]
---

# ADR-[NNN]: [CHOICE] as [CATEGORY]

## Context

[What problem is being solved and under what constraints]

## Options Considered

### Option 1: [Alternative]
- Pro: [advantage]
- Con: [disadvantage]

## Decision

We chose **[CHOICE]** because [primary motivation].

## Consequences

**Positive:**
- [benefit]

**Negative:**
- [tradeoff]

## Related

- [docs/specs/tech-stack.md](../specs/tech-stack.md)
```

A Draft ADR may contain only the Decision section plus `<!-- TODO: -->` markers for the rest.

Superseded and Deprecated ADRs with no code references are deleted. Git history is the archive.

## design/ux-decisions/NNN-[slug].md

Same shape, status values, and rename rules as an ADR, with `# UX-[NNN]:` as the title prefix, `[CHOICE] for [Context]` as the title shape, independent numbering, and `## Related` pointing at other UX decisions or `DESIGN.md` rules. Never file one under `docs/adrs/`, and never title a file in this tree `ADR-`.

```markdown
---
status: Active
date: [TODAY]
---

# UX-[NNN]: [CHOICE] for [Context]

## Context

[User problem or interaction tension, and who experiences it]

## Options Considered

### Option 1: [Alternative]
- Pro: [advantage]
- Con: [disadvantage]

## Decision

We chose **[CHOICE]** because [primary motivation].

## Consequences

**Positive:**
- [benefit]

**Negative:**
- [tradeoff]

## Related

- [UX-NNN or DESIGN.md rule]
```

<!-- SECTION: ux-tbd-comment -->
## UX-TBD Comment

When UI code has no governing UX decision and the intent is unclear, flag it instead of inventing a reason:

```tsx
// UX-TBD: empty-state copy, agent-generated and not reviewed
<EmptyState message="..." />
```

It is a flag, not a decision. It resolves by capturing a UX decision and replacing it with `// UX-NNN: [note]`, by removing it when a designer says it does not matter, or by the code being rewritten. Skip it for trivial layout scaffolding.

<!-- SECTION: bad-patterns -->
## patterns/bad/anti-patterns.md

The file starts with this header so that anyone, with or without the plugin, can add an entry:

```markdown
# Anti-Patterns

Common mistakes to avoid in this codebase. Add a section per anti-pattern in this shape:

## [Category]: [Description]

**Severity:** Critical | High | Medium | Low

### Don't Do This
```[language]
[bad example]
```

**Problems:**
- [Issue]

### Do This Instead
```[language]
[correct example]
```

**Why:** [Explanation]

---
```

Severity: Critical (security, data loss, accessibility failures), High (performance, maintenance burden), Medium (code smell, inconsistency), Low (style).

<!-- SECTION: agent-instructions -->
## CLAUDE.md / AGENTS.md

The generated file routes an agent to the right document at the right moment and carries the few rules that must be known before any work. It does not demand reading everything before every edit; that burns context and slows work. Keep it under 60 lines. Fill the bracketed parts from the repo at generation time. Include the design lines only when `DESIGN.md` or `design/` exists.

```markdown
# Agent Instructions for [PROJECT_NAME]

[One-paragraph project description]

## Where intent lives

Code shows what the system does. These files record why, so deliberate choices can be told apart from expedient ones:

- `docs/adrs/` records architecture decisions. Read the relevant ADR when a change touches a documented choice; feature specs list theirs in `related_adrs`. If code contradicts an Active decision, say so before following either.
- `docs/specs/features/` holds feature specs. Read one when implementing or changing that feature.
- `docs/specs/boundaries.md` has the full list of what is safe, what to ask about, and what is never done, including module-scoped rules.
- `patterns/good/` holds examples to follow: [list the files present, e.g. `repository.ts`, `api-handler.ts`]. `patterns/bad/anti-patterns.md` lists what to avoid. Check them when writing similar code.
- `DESIGN.md` holds cross-cutting design rules. Read it for any UI work.
- `design/ux-decisions/` records UX decisions. Read the relevant one when changing the affected surface. UX rationale goes there, never under `docs/adrs/`.

## Autonomy and limits

Safe without asking: [copy the Safe Without Asking bullets from boundaries.md, one line].
Ask first: [copy the Ask First bullets, one line].
Never: [copy the Never Do bullets, one line]. If a request would violate one of these, say which rule and propose an alternative.

## Traceability

When code implements a documented decision, add a one-line reference and leave the rationale in the decision file:

```
// ADR-NNN: [brief note]
// UX-NNN: [brief note]
// UX-TBD: [what is unclear]   <- UI with no governing decision; flag, do not invent a reason
```

## Recording new intent

When the user states a decision with a reason, corrects a pattern, or names something to avoid, offer to record it. With the Blueprint plugin, use `/blueprint-mode:decide`, `/blueprint-mode:require`, `/blueprint-mode:good-pattern`, or `/blueprint-mode:bad-pattern`. Without it, copy the shape of an existing file in the target directory; if the directory is empty, the formats are at https://github.com/rickardp/blueprint-mode/blob/main/plugins/blueprint-mode/skills/_templates/TEMPLATES.md. The next decision number is one past the highest in its directory.

## Commands

```bash
[test / lint / typecheck commands]
```
